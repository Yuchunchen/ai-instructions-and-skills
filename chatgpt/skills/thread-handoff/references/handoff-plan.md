# 接續計畫與接手核對

**共通規格：v1.1｜2026-10-11**

維護來源：GitHub 的 `chatgpt/skills/work-handoff/references/handoff-plan.md`。三個 handoff skills 隨包附帶相同內容；只讀本包。

## 何時加入計畫

使用者要求「handoff plan／交班加計畫」，或接手的多步工作需要交代依賴、順序與驗收時，產生可執行的接續計畫。已有計畫就核對並更新剩餘部分，不重啟規劃或重複核准；單一明確工作以具體下一步及完成條件即可。

方向尚未定案時，把近期查核／比較列為計畫，不替使用者完成關鍵決策。只要求計畫，不表示已授權執行。獨立第二意見的成果是審查報告，未授權就不修改原件。

## 計畫內容

以目前決策與證據為起點，依需要列出：
- 接手目標、已完成部分與本次交付物。
- 各步動作、所需來源／輸入、依賴、預期產出及完成條件。
- 已確定的方法與可由接手者判斷的實作細節。
- 已授權範圍、停止點與真正需新核准的動作。
- 重要未知及取得答案後的分支；能獨立推進的部分先保留。
- 與風險相稱的驗證；不可逆或影響較大變更才補適用的回復方式。
- 下一個具體動作，而非只寫「繼續處理」。

不補造 Owner、期限、測量基準、指令或檔案路徑。不強制建立追蹤任務、拆成多份檔案、使用平行代理、提交 Git、結束 session 或另開對話。這些動作依本次任務及已有授權決定。

## 分支與 Checkpoint 的接續契約

- 沿用穩定的 plan_id、plan_revision 與 step_id，不因交班重新編號；保留原目標、範圍、所有未完成主線與依賴。
- 每個分支保留 branch_id、父步驟／父分支與 return_to。巢狀分支逐層返回，主線 A、B、C、D、E 中的 B1-a／B1-b／B1-c 不能取代 C、D、E。
- 分支結果逐項分成「已採用／已否決／待驗證」，附依據及受影響步驟；回到父節點更新依賴、驗收與下一步。待驗證不解除硬依賴，已採用不等於已部署。
- 若採用結果會改變已確認目標、範圍或重要取捨，先請使用者裁定；既有授權內的實作細節不重複核准，無關工作繼續。
- 交付可恢復 checkpoint：ID／時間／修訂版、主線與分支位置、已驗證 artifact 的位置／版本／證據、未完成及阻塞、未同步或結果不明的外部操作（標的／ID／最後觀察／回查方式），以及下一個可執行動作和完成條件。
- 接手先讀最新計畫、必要來源與外部狀態，比對 checkpoint／舊交班稿；舊對話只供背景。新版來源不自動核准新目標，矛盾未解就暫停相依段落，保留他人修改。
- 涉及 Notion 時，只在已授權位置保存工作狀態，與學習紀錄分開；原始 artifact 留在 GitHub／正式文件。寫前重讀並比較基線／現況／擬議修改，局部寫入並回讀。同段衝突先停；單一寫入者只是協作約定，不能保證鎖定或原子性。

## 各層完成證據

依本次授權範圍分別列來源 artifact、帳號保存／同步、適用的 Notion 工作狀態更新與回讀。未授權項目標不適用，不為填滿完成表新增操作。來源成功、帳號失敗是部分完成，保留缺少部分及回查／重試步驟；任何逾時或不明操作先查結果，不直接再新增或重寫。

來源保存、帳號內容已回讀、實際 Runtime 使用是不同證據；靜態檢查、合成案例與真實跨 AI 執行分別回報。交班稿或計畫完成不等於已執行；只要求交班／規劃時交付文字即止，不自動同步外部系統。


## 接手時的最小核對

- 讀取即將使用或修改的必要現況，核對標的、版本、狀態與適用專案規則。不要因交班就全面重查所有資料。
- 「不重做」是不重複已完成的工作，不禁止必要回讀、確認環境差異，或在新證據下檢查舊結論。
- 文件／程式已變動時，保留他人變更並調整剩餘工作；只有影響方向、風險或授權時才回問。
- 外部寫入、提交或建立操作逾時／回應不明時，先依已知 ID、標題、內容或版本回查；未釐清前不得直接再次新增／寫入。
- 若來源不可存取，指出受阻步驟和解除條件，繼續可獨立完成的授權工作。

## 起始指令原則

要求接手者沿用現行決策、授權與計畫，做必要現況核對後從具體下一步做到完成條件。不要無條件要求先提計畫等待批准，也不要要求忽略阻塞或禁止所有提問。接手者的實際工具、權限與專案規則仍適用；交班本身不擴權。
