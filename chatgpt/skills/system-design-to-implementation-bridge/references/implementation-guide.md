# 操作契約、試行與回復

本檔是按情境選用的參考。依 SKILL.md 已選模式、實際風險與使用者要求挑選相關段落；沒有相關問題時可明說未發現，不為數量或格式新增問題、產物或核准。

## Step 5｜Tool Mapping

對每個需要使用的工具說明：

### Tool

工具名稱。

### Purpose

它在本流程中解決什麼問題。

### Location

實際放在哪個 Project、Thread、資料夾、文件或頁面。

### Owner

誰負責操作與維護。

### Trigger

什麼情況會啟動。

### Input

需要提供什麼。

### Output

必須產生什麼。

### Handoff

下一步交給誰、使用哪一種 Handoff。

### Canonical Status

該工具中的內容是：

* 討論稿
* 工作稿
* 暫定稿
* 正式稿
* Canonical

不要只列工具名稱。

## Step 6｜建立最小操作契約

對需要明確責任與交接的核心流程，依適用性定義：

### Owner

必須推動完成的人。

### Trigger

啟動條件。

### Input

啟動時需要的資料、決策或文件。

### Action

實際執行的動作。

### Output

完成後產生的可驗證成果。

### Reviewer／Approver

誰檢查或裁定。

### Handoff

交給下一個角色或工具的方式。

### Canonical Source

正式版本的位置。

### Failure Path

無法完成或資訊不足時如何處理。

## Step 7｜選擇第一個 Pilot

不要直接全面上線。

需要試行的新流程，其第一個 Pilot 應符合：

* 規模小
* 可以完成整個循環
* 結果容易驗證
* 不涉及高風險不可逆修改
* 可以測試主要交接點
* 失敗成本低

本次需要 Pilot 時，按風險檢查：

1. Trigger 是否清楚。
2. Input 是否足夠。
3. Owner 是否真的會執行。
4. 工具交接是否可行。
5. Output 是否可使用。
6. Canonical 是否正確更新。
7. 是否增加不必要維護負擔。

新流程若無法指定可完成循環的 Pilot，重新縮小試行範圍；已驗證的小流程可沿用相稱的結果檢查。

## Step 8｜建立實作順序

只提供足以啟動與試運轉的順序，不取代完整 Iterative Work Planner。

建議使用以下階段：

### Phase 0｜準備

* 確認已定案設計
* 確認工具與權限
* 確認 Owner
* 確認 Canonical Source

### Phase 1｜建立最小承載環境

* 建立必要 Thread、Project、文件或資料夾
* 不建立非必要資料庫或自動化
* 放入必要 Instruction 與參考資料

### Phase 2｜執行 Pilot

* 使用一個真實案例
* 完成完整操作循環
* 記錄問題

### Phase 3｜驗證與修正

* 檢查結果
* 修正交接、責任或工具配置
* 確認維護負擔

### Phase 4｜擴展

* Pilot 成功後才複製到其他模組、團隊或文件
* 必要時交給 Iterative Work Planner 做完整拆解

## Step 9｜產生 Step-by-step Guide

逐步指南必須具體到使用者可以操作。

依本次操作需要選用下列欄位；已在共用脈絡清楚的資訊不必每步重複：

### Step 編號與名稱

### 使用工具

在哪一個工具中操作。

### 操作位置

Project、Thread、文件、頁面或資料夾。

### 執行者

誰操作。

### 操作內容

實際建立、貼入、修改、確認或送出的內容。

### 輸入

需要準備的資料。

### 預期結果

完成後應看到什麼。

### 驗證

如何確認這一步正確。

### 下一步

交給誰或進入哪個工具。

不要使用以下空泛表述：

* 建立一個頁面
* 開一個 Thread
* 交給 Claude
* 建立看板
* 使用自動化
* 更新 Architecture

除非同時說明具體位置、內容、Owner、輸入、輸出與驗證。

## Step 10｜驗證計畫

依實際流程選擇相關驗證層次；不適用者可省略，說明必要限制。

### 操作驗證

流程是否可以從頭走到尾。

### 內容驗證

輸出是否正確、完整、可使用。

### 交接驗證

下一個人或 AI 是否能理解並接續。

### 治理驗證

正式版本、權限、Owner 與決策紀錄是否正確。

可選擇的成功指標包括：

* 不需要主持人重複解釋背景
* 沒有產生兩份正式版本
* Handoff 可被下一個 AI 正確執行
* Owner 知道何時與如何更新
* Pilot 能在預期時間內完成
* 產出可直接進入下一階段
* 未增加無人維護的新文件或系統

## Step 11｜回復與停止方式

涉及持續運作或狀態變更的方案，按需要說明：

### 何時停止

例如：

* Pilot 無法完成
* 維護成本高於效益
* Owner 不明
* 工具無法交接
* 產生版本分歧
* 關鍵安全或法規問題未解決

### 如何回復

例如：

* 回到原有人工流程
* 恢復前一版正式文件
* 關閉暫時建立的 Thread 或資料庫
* 停止自動化
* 保留實驗紀錄但不進入 Canonical
* 將未定案內容移回討論區

### 誰有權決定回復

明確指定 Decision Owner。

不要將回復方式寫成「必要時再處理」。
