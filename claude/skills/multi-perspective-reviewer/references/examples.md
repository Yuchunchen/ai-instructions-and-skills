# 多視角情境範例

本檔供相關情境按需查閱。依 SKILL.md 已選模式、實際風險與使用者要求挑選段落；沒有相關問題時可明說未發現，不為數量或格式新增問題、產物或核准。範例中的工具、角色與專案條件不自動套用到當前任務。

# 使用範例一｜Proposal Operating System

使用者：

「請從不同角色檢查目前 POS 的實作方案。」

建議視角：

* 計畫主持人
* 計畫書 Thread 使用者
* Claude／Cowork 正式整合者
* 模組負責人
* 維護者
* 最終送件行政窗口

可能發現：

### 計畫主持人

可能價值：

* 可把策略裁定與日常整合分開。

可能疑慮：

* 仍需手動在多個 Thread 與 Claude 之間搬運內容。

### 模組負責人

可能疑慮：

* 不知道應提供什麼格式、何時提供、交給哪個 Thread。

### Claude／Cowork

可能疑慮：

* 已定案、暫定與腦暴內容未清楚區分，正式主稿容易被污染。

### 維護者

可能疑慮：

* 若同時存在作戰板、Thread 摘要、Claude 主稿與 Notion，可能形成多個正式來源。

共同問題：

* Handoff 與 Canonical Source 必須清楚。

結論可能是：

> Proceed with Required Changes：先完成一次端到端 Pilot，證明交接可行，再決定是否建立作戰板。

# 使用範例二｜健康台灣計畫書

使用者：

「請從不同角色檢查花東縱谷醫療生命線計畫。」

建議視角：

* 偏鄉居民／病人
* 三院第一線醫療人員
* 總主持人
* 主計室
* 三院維運團隊
* 健康台灣審查委員

可能衝突：

* 玉里共同能力建置效率
  vs
  審查者對資源集中玉里的疑慮

* 鳳林維持急診可近性
  vs
  第一線人力負荷及可持續性

* 臺東長照急症支援擴張
  vs
  現有人力與既有醫院合作邊界

本 Skill 應指出問題與決策需求，但不直接重新改寫整份計畫書。

# 使用範例三｜差勤系統

使用者：

「從不同角色檢查新的打卡制度。」

建議視角：

* 一般員工
* 輪班與單人值班人員
* 單位主管
* 人事室
* 資訊室
* 法規／勞動管理
* 院方管理者

可能共同問題：

* 系統規則與真實工作流程不一致。
* 責任被轉嫁給第一線與單位主管。
* 例外處理缺乏一致標準。

可能角色衝突：

* 如實呈現工時
  vs
  行政負擔與現場彈性

結論可能是：

> Return to Design：先修正例外處理與主管權限，再推動全面上線。

# 使用範例四｜AI 人生故事照護

使用者：

「從不同角色檢查 AI 人生故事照護方案。」

建議視角：

* 住民
* 家屬
* 照護人員
* 臨床人員
* 機構管理者
* 個資與倫理
* 系統維護者

重要問題可能包括：

* 住民是否真正同意故事被記錄與使用。
* 家屬提供內容是否等同住民意願。
* 照護人員是否有時間閱讀並轉化成照護行動。
* 故事中的敏感資料如何保存、修正與刪除。
* 如何證明故事真的改善照護，而非只產生漂亮文本。

本 Skill 可建議進入正式倫理與個資 Review，但不能取代該審查。
