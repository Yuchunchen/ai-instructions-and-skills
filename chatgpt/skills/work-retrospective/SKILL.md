# Work Retrospective

**版本：v1.0.0｜2026-10-18**

找出本次工作為何順利、受阻或重工，以及下一次值得保留或改變的最小做法。適用程式、計畫與論文工作，不固定產生問題數量或強迫新增規則。

## 範圍與來源

以使用者指定工作為範圍；未指定則以目前可見工作為範圍。只讀可存取且已授權的對話、成果版本、測試與工作紀錄；缺少紀錄時交付有範圍限制的觀察，不推測其他分支內容、不越過受限路徑、不索取憑證或為復盤新增存取權。引用能定位問題的最少證據，避免重述敏感資料。

只要目前進度／變更驗收，使用可用的 conversation-review；只要接著做，延續既有工作，不插入復盤。

## 復盤方式

1. 對照原目標、限制、已確認計畫與實際結果，挑出有證據且影響未來工作的事件，也可保留有效做法。
2. 將「觀察到的事件」與「原因」分開。原因標已確認或假說，寫明支持來源與待驗證處；相關性不當因果，缺乏日誌不等於未執行。
3. 為重要事件提出最小改善，先檢查現有方法是否已存在但未使用或失效，再考慮新增：
   - 導覽／來源定位：改善入口、檔案指標或分支返回點。
   - 可機械檢查的錯誤：優先既有檢查、自動測試或清單驗證，不把每次失誤都寫成全域提示詞。
   - 需判斷的取捨：才考慮局部審閱準則，限定適用情境。
   - 工具成本／資訊缺口：比較更省步驟的方法；額外權限僅列建議，不自動取得。
4. 為建議附可觀察驗證方式、適用範圍與下一步。按影響與成本排序；無有價值改善時直接說明，不製造問題。
5. 回到既有主線：保留 plan_revision、穩定步驟 ID、父分支／返回點（已有時）。區分「建議／已採用／已實施／已驗證」；只有已採用改善才進入現行計畫，是否重排由可用 planner 或等效接續流程處理。

## 輸出與邊界

預設精簡條列：「事件與證據 → 原因及可信程度 → 最小改善 → 如何驗證／下一步」。需要時標 Owner 與解除條件；不強制套完整報告。

復盤請求本身不授權修改 Skills、全域指令、程式、CI、帳號權限或 Notion。外層已有明確修改授權時，沿用該授權完成相應工作及檢查；否則停在建議。不得把單次事件自動升格成永久規則。程式檢查通過不證明研究結論、醫療安全或組織核准。

設計與維護時讀 [examples-and-checks.md](references/examples-and-checks.md)；一般復盤不必載入案例。
