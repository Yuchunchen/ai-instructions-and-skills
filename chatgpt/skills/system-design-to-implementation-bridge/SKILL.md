# System Design to Implementation Bridge

**來源修訂：2026-09-06｜第二輪檢查後修訂；原文未標語意版本**

將已收斂、但尚缺承載工具與操作方式的設計轉成可試行的方案。先分清「設計方案完成」與「實際執行完成」。

## 何時使用

核心目標與範圍已有共識，使用者需要決定如何放入現有工具、角色與工作流時使用。「下一步」「逐步指南」或出現新文件，不單獨觸發本 Skill。
只有改寫、證據審查、詳細任務排程或既定步驟執行時，直接處理該需求。重大方向仍不清楚才用可用的 `unknown-pass`，不在此重做完整探索。

## 選擇模式與參考

- 輕量：單一流程、少量工具。交付位置、Owner／Trigger／Input／Output、具體步驟、驗證與回復即可。
- 標準：多工具、長期維護或交接。需要比較工具配置時讀 [工具模式](references/tool-modes.md)；需要詳細操作契約、試行、驗證及回復時讀 [實作指引](references/implementation-guide.md) 的相關段落。
- 情境不熟悉時讀 [使用範例](references/examples.md)。範例不是所有任務的指定架構。

選定模式決定適用欄位；沒有交接、持續維護或正式版本的任務可省略對應項目，不為完整性新增制度。參考不可讀時依本檔形成有界方案，標示未取得的細節。

## 從設計到可行動方案

1. 簡述已定案目標、成功條件、範圍與不可變更事項。區分已確認、暫定與待確認。
2. 作最低必要的 Design Readiness 判斷：
   - **Ready**：目標、角色、主要輸入輸出、工具權限與驗證方式足以操作。
   - **Ready with Assumptions**：可在清楚假設下小規模試行，列出第一個驗證點。
   - **Not Ready**：關鍵未知會改變架構或安全可行性；指出缺口及最重要問題，保留依賴該決策的部分。
3. 優先沿用現有工具。對真正需要的工具／產物說明用途、位置、主責、觸發、輸入、輸出及必要的交接。長期產物再定義維護責任與頻率。
4. 提供使用者可操作的步驟：在哪裡、由誰、做什麼、預期得到什麼，以及如何確認。詳細 Phase／Task 排程只有需要時才交給 `iterative-work-planner`。
5. 對新建、未驗證的持續流程或準備擴大的系統，選一個能走完整循環的 Pilot；已驗證的小流程可直接做相稱的結果檢查，說明沿用依據，不再另建 Pilot。
6. 定義成功、失敗時的處理、回復方式與有權決定的人。新風險、範圍擴張與必要正式核准才形成新增核准點；沿用已授權範圍與已確認計畫。

## 交付、驗證與停止

使用 `[System Design to Implementation Bridge]` 或 `[Implementation Bridge｜Light]`。依本次需要交付 Readiness、操作位置與責任、步驟、驗證、回復及下一個動作；其餘欄位按需加入。

方案完成：必要步驟可執行、成功與失敗條件清楚、阻塞與授權明確，下一步可開始。執行完成：整體任務要求的操作已做完並取得相稱的驗證結果。只要求方案就交付方案；同時要求實作且已授權可執行時，由當前工作接續到結果驗證，不只交計畫就停止。

驗證挑選相關項目：操作能否走通、內容是否正確、接手者是否可續作、正式來源與權限是否正確。沒有交接不另設交接測試。無法測試時明說哪些只是方案。
發現關鍵安全／權限未解、版本分歧或工具無法交接時，停止受影響操作，保留已完成成果，說明可修正路徑與必要回復；不把新文件或流程圖存在當成系統已運作。
