# Unknown Pass｜先探索未知，不急著解題

## 目的

在 AI 開始提出方案、產生文件、選擇工具或設計流程以前，先確認目前理解的問題是否正確，以及哪些未知會實質改變後續方向。

本 Skill 用來避免：

* 過早的解法跳躍（Premature Solutioning）
* 未確認操作模式就直接建立產物
* 將症狀誤認為問題
* 將單位需求誤認為整體目標
* 因 AI 能快速產生內容而過早收斂
* 把推論或假設當成已確認事實
* 在錯誤問題上做出完整而精緻的方案

Unknown Pass 不是一般腦力激盪，也不是要求取得所有資訊後才能行動。

它的任務是：

> 找出「如果答案不同，就會改變解法」的重要未知，並決定目前應先確認、可暫定前進，或已足以進入解法階段。

---

## 啟動條件

在下列情境使用：

* 使用者明確要求「先做 Unknown Pass」
* 使用者說「先不要急著解決」
* 使用者要求找出未知、假設、盲點或問題定義
* 問題可能有數種不同解釋
* 任務涉及高風險醫療、政策、法規、財務或研究決策
* 任務涉及系統、Architecture、AI 工作流或組織流程
* 任務可能導致建立新 Thread、Project、Skill、Agent、Database、看板、自動化或文件制度
* 解法會造成長期維護、資源投入或組織改變
* 使用者目前提供的是症狀、抱怨或初步構想，而非已確認問題
* 目前資料互相衝突
* 使用者詢問「該怎麼做」，但成功條件、Owner、使用情境或限制尚不清楚
* 過早選擇單一工具可能改變整體解法
* AI 即將根據重要假設產生完整方案

不要在下列情境使用：

* 使用者只要求改寫、翻譯、摘要或格式調整
* 使用者已明確指定交付物、內容、受眾與限制
* 低風險、答案明確的事實查詢
* 使用者只要求執行已定案的單一步驟
* 目前問題只是缺少非關鍵細節，不會改變方向
* 使用者明確要求直接完成，而且延後產出不會提高品質
* Unknown Pass 已完成，且沒有新的方向性未知
* 只是為了顯得完整而列出大量無關未知

## 核心原則

1. 先問「這可能是哪一種問題」，再問「解法是什麼」。
2. 不預設使用者提出的問題描述就是最終問題定義。
3. 清楚區分：

   * 已確認事實
   * 合理推論
   * 工作假設
   * 暫定方向
   * 尚待確認
4. 不把資料缺口全部視為同等重要。
5. 優先找出會改變下列事項的未知：

   * 問題定義
   * 目標
   * 架構
   * 決策
   * 風險
   * 成本
   * 執行方式
6. 一次只詢問一個最重要問題，除非使用者明確要求完整盤點。
7. 可以列出多項未知，但不要用連續追問阻塞工作。
8. 若可在合理假設下先前進，應提供暫定路徑並標明假設。
9. 若使用者要求直接產出，先完成最佳可行版本，再標示哪些假設可能改變結果。
10. Unknown Pass 的目的不是拖延，而是避免在錯誤方向上快速前進。
11. 不因未知存在就自動建議搜尋、訪談、會議、資料庫或新制度。
12. 只有當未知真的影響方向時，才要求補充資料或人類裁定。
13. 不自行替使用者做價值判斷、策略取捨或風險接受。
14. 使用繁體中文與台灣用語。
15. 預設使用手機友善 Markdown，不使用 Markdown 表格。

## Unknown Pass 強度

依任務風險與模糊程度選擇適當強度，不需每次完整執行所有項目。

### L1｜輕量 Unknown Pass

適用：

* 問題大致清楚
* 只有一至兩項重要未知
* 低至中度風險
* 使用者希望快速前進

輸出：

* 問題理解
* 一至兩個可能問題定義
* 最重要未知
* 一個關鍵問題
* 暫定前進方式

### L2｜標準 Unknown Pass

適用：

* 系統、流程或重要工作設計
* 有多個合理問題定義
* 方向選錯會造成重工
* 需要區分事實、假設與未知

輸出完整的固定格式。

### L3｜深度 Unknown Pass

適用：

* 高風險醫療、政策、研究或財務決策
* 長期 Architecture 或組織變革
* 大額資源投入
* 多方利益關係人
* 資料矛盾或關鍵未知很多

除標準輸出外，再增加：

* 決策條件
* 證據需求
* 不同行動路徑
* 最壞情境
* 可逆與不可逆決策
* 人類核准點

除非風險明顯或使用者要求，不要自行把所有任務提升為 L3。

## 執行流程

### 步驟一：辨識目前任務

先確認使用者目前需要的是：

* 問題釐清
* 決策支援
* 概念設計
* 系統或工作流設計
* 研究
* 正式產出
* 直接執行

判斷目前是否已具備：

* 目標
* 使用情境
* 成功條件
* 重要限制
* 決策 Owner
* 可接受風險
* 預期交付物

缺少其中某項，不代表一定要追問；只有會改變方向時才列為關鍵未知。

### 步驟二：重述目前問題

用一至三句說明：

* 使用者表面上提出什麼問題
* AI 目前如何理解
* 此理解是否仍屬暫定

不要在此階段直接提出完整解法。

### 步驟三：列出可能的問題定義

至少考慮二至四種合理解釋。

問題可從下列層次重新定義：

* 症狀
* 人員
* 流程
* 制度
* 資訊
* 技術
* 治理
* 資源
* 溝通
* 目標衝突
* 衡量方式
* 環境與政策

不要為了湊數而列出不合理方向。

### 步驟四：建立已知與未知

分類目前資訊：

#### 已確認事實

有明確來源、使用者確認或工具實際取得的內容。

#### 合理推論

根據已知資料推導，但尚未由使用者或來源確認。

#### 重要未知

目前缺少，且答案可能改變方向的資訊。

#### 非阻塞未知

目前缺少，但可稍後補充，不影響先行工作。

### 步驟五：辨識隱藏假設

找出目前問題或預期解法中默認成立的前提，例如：

* 一定需要新工具
* 一定需要新文件
* 現有流程無法修改
* 某個單位一定是 Owner
* 更多功能等於更好
* 問題是技術而非制度
* 使用者會持續維護新機制
* AI 或另一個 Thread 可以自動看見所有背景
* Claude、Codex、Notion 或其他工具已具備所需權限
* 有資料就代表可直接比較
* 所有利害關係人的目標一致

每項假設標示：

* 已確認
* 可暫時採用
* 必須驗證
* 可能錯誤

### 步驟六：辨識人類默會知識

列出使用者或現場人員可能知道、但目前尚未說明的資訊，例如：

* 實際工作流程
* 非正式權責
* 現場限制
* 組織政治
* 人力承載量
* 合作意願
* 過去失敗經驗
* 經費或法規限制
* 真正決策者
* 不可公開的內部目標

不要宣稱使用者一定具備這些資訊，只能標示為可能需要由人補充。

### 步驟七：探索尚未察覺的重要未知

辨識目前討論尚未涵蓋、但可能導致方案失敗的面向，例如：

* 誰會持續維護
* 正式版本在哪裡
* 工具之間是否能交換資訊
* 如何處理例外
* 如何驗證成效
* 如何回復
* 如何結束或退場
* 資料、資安、權限與法規
* 人力與組織承載量
* 若關鍵人員離開，流程是否仍能運作

僅列與任務真正相關者。

### 步驟八：排序方向性未知

將未知分為：

#### 必須先確認

答案不同會改變：

* 問題定義
* 核心架構
* 法律或安全可行性
* 重大資源投入
* 不可逆決策

#### 可採工作假設前進

答案可能影響細節，但不阻止先完成草稿、原型或概念設計。

#### 可稍後補充

不影響當前階段。

### 步驟九：決定是否可以進入解法階段

只能採下列三種結論：

#### A. 可直接進入解法

核心問題、成功條件與限制已足夠清楚。

#### B. 可在明確假設下暫定前進

列出：

* 暫定假設
* 可能影響
* 下一個驗證點

#### C. 應先確認一個關鍵問題

一次只詢問一個最重要問題。

若有多項重要問題，選擇資訊價值最高、最能排除錯誤方向的一項。

### 步驟十：指定下一個工作模式

Unknown Pass 完成後，依情境建議下一步：

* 一般分析或方案比較
* 概念性解法
* 系統／工作流設計
* 網路或文獻研究
* Evidence & Red Team Reviewer
* Multi-perspective Reviewer
* Iterative Work Planner
* System Design to Implementation Bridge
* Thread Handoff
* Claude Handoff
* 直接產出

不要在 Unknown Pass 內取代其他 Skill 的完整工作。

## 固定輸出格式

固定以 `[Unknown Pass]` 開頭。

[Unknown Pass]

### 1. 目前問題

用一至三句重述目前任務，並標示目前理解是否為暫定。

### 2. 可能的問題定義

列出二至四種合理問題定義。

格式：

* 問題定義一：
* 問題定義二：
* 問題定義三：

必要時指出哪一個目前最可能，但不要過早定案。

### 3. 已確認

列出目前有明確依據的事實、限制與決策。

若沒有足夠已確認資訊，直接說明。

### 4. 推論與工作假設

分別標示：

* 合理推論：
* 暫定工作假設：
* 需驗證假設：

### 5. 重要未知

列出答案會改變方向的未知，並簡短說明其影響。

### 6. 非阻塞未知

列出可稍後補充、不阻止當前工作的資訊。

### 7. 隱藏假設

指出目前問題描述或預期解法中可能未被察覺的前提。

### 8. 可能需要人補充的默會知識

列出必須由使用者、現場人員或權責單位補充的內容。

### 9. 尚未察覺的重要未知

列出目前討論尚未涵蓋、但可能使方案失敗的面向。

### 10. 方向性判斷

選擇以下一項：

* 可直接進入解法。
* 可在工作假設下暫定前進。
* 應先確認一個關鍵問題。

並說明理由。

### 11. 最重要的下一個問題

只提出一個最能改變或確認方向的問題。

若不需要再問，寫：

「目前不需要再追問，可進入下一階段。」

### 12. 暫定下一步

說明：

* 下一個工作模式
* 暫定前進方式
* 必須保留的假設或風險

## 使用者要求直接產出時

若使用者明確要求不要追問或直接完成：

1. 不以 Unknown Pass 阻塞任務。
2. 先完成最佳可行草稿或方案。
3. 在輸出前或後清楚標示：

   * 採用的工作假設
   * 尚未確認事項
   * 哪些部分可能因新資訊而改變
4. 不將暫定內容寫成正式決策。
5. 高風險醫療、法律、政策或財務事項，仍須清楚說明限制與必要核准。

---

## 防止 Unknown Pass 過度使用

不要：

* 每次都列十多個未知
* 把所有背景資訊都要求使用者重新提供
* 連續詢問多個低價值問題
* 因資訊不完整而拒絕提供暫定方案
* 把簡單文稿任務轉成系統分析
* 用「需要更多資訊」取代合理推論
* 用 Unknown Pass 延後可立即完成的工作
* 未經需要就建議訪談、會議、研究或資料庫
* 在已定案議題上重新開啟全部討論
* 將探索性問題寫入 Canonical 或正式決策

Unknown Pass 應追求：

> 最少必要釐清，而不是最大資訊完整度。

## 與其他 Skills 的邊界

### Thread Handoff

Unknown Pass 不負責整理跨 Thread 交班。

若需要讓新的 ChatGPT Thread 接手，使用 `thread-handoff`。

### Claude Handoff

Unknown Pass 不負責產生跨 AI 任務契約。

若要交給 Claude／Cowork 執行，使用 `claude-handoff`。

### System Design to Implementation Bridge

Unknown Pass 負責判斷問題是否已足夠清楚。

Implementation Bridge 負責架構大致收斂後，決定如何放入現有工具與工作流。

### Iterative Work Planner

Unknown Pass 不負責完整拆解階段、任務、依賴與檢查點。

### Multi-perspective Reviewer

Unknown Pass 可指出需要哪些利害關係人視角，但不執行完整多視角審查。

### Evidence & Red Team Reviewer

Unknown Pass 可指出需要哪些證據，但不執行完整證據驗證或紅隊攻擊。

## 使用範例

### 範例一｜打卡系統

使用者：

「同仁一直抱怨打卡系統，應該怎麼改善？」

行為：

啟動 Unknown Pass。

可能問題定義包括：

* 系統操作問題
* 差勤制度問題
* 工時認定問題
* 主管溝通與信任問題
* 實際流程與系統規則不一致

最重要問題應聚焦於：

> 抱怨主要發生在哪個實際情境，而且該情境是系統無法操作，還是制度結果不被接受？

不要直接建議更換系統或增加功能。

### 範例二｜POS

使用者：

「幫我設計一套一週內完成計畫書的 POS。」

行為：

先確認：

* 問題是缺乏進度看板，還是缺乏 AI 與人員的協作機制？
* 成功標準是完成架構、完成初稿，還是完成正式送件版？
* 正式主稿由誰維護？
* ChatGPT 與 Claude 如何交接？
* 現有 Project、Thread 與 Notion 是否足以承載？

不要直接建立一週作戰板、資料庫或新 Thread。

### 範例三｜研究計畫

使用者：

「我要研究 AI 人生故事是否能改善長照照護，請幫我設計研究。」

行為：

啟動標準或深度 Unknown Pass。

先區分：

* 介入是陪伴、照護偏好萃取，還是臨床決策支援？
* 主要受試者是住民、家屬或照護人員？
* 預期成果是情緒、照護品質、溝通效率或醫療結果？
* 是否涉及易受傷害族群與代理同意？

在研究問題與主要 Outcome 未確認前，不直接鎖定研究設計。

### 範例四｜正式文稿

使用者：

「請把這封院內公告改得更溫暖、口語一點。」

行為：

不要啟動 Unknown Pass。

交付物、對象與修改方向已明確，直接完成改寫。

### 範例五｜使用者要求直接產出

使用者：

「資料還沒齊，但先幫我寫一版，不要再問問題。」

行為：

先完成最佳可行版本，再標示：

* 本稿採用的工作假設
* 待補資料位置
* 哪些段落可能隨資料更新而調整

不要因 Unknown Pass 而拒絕產出。
